# Правила коммитов для exception_blog

## 1. Префиксы типов изменений
- `doc`: Изменения в документации
- `refactor`: Рефакторинг кода
- `fix`: Исправление ошибок
- `feat`: Новая функциональность
- `test`: Изменения тестов
- `config`: Настройки/конфигурация
- `deps`: Зависимости

## 2. Формат сообщения
```
<префикс>: <краткое описание> [эмодзи?]
```
Пример: `feat: Добавлена аутентификация через VK 🔐`

## 3. Тело коммита
- Тезисное перечисление изменений
- Каждый пункт с дефиса
- Маркдаун-форматирование
Пример:
```
doc: Обновление документации
- Добавлен раздел установки
- Описаны правила коммитов
- Обновлен pyproject.toml
```

## 4. Ключевые слова для задач
```mermaid
graph LR
    A[Связь с задачей] --> B{Тип связи}
    B -->|Автоматическое закрытие| C(Closes #)
    B -->|Связь без закрытия| D(Related to #)
    B -->|Локальная задача| E(Local task #)
    B -->|Дополнительная ссылка| F(See also #)
```

- **Closes #12**: Коммит решает задачу, автоматически закрывает issue
- **Related to #15**: Коммит связан с задачей, но не закрывает её
- **Local task #3**: Коммит соответствует задаче из doc/tasks/tasks.md
- **See also #7**: Дополнительная релевантная задача

## 5. Примеры использования

```bash
git status --porcelain --untracked-files=all - для получения списка измененных и новых файлов
git diff ... для получения списка изменений в файлах
```

### Пример с Closes
```
fix: Исправление загрузки изображений
- Валидация MIME-типов
- Исправление таймаута S3
- Обработка ошибок подключения
Closes #18
```

### Пример с Related to
```
doc: Добавление CONTRIBUTING.md
- Правила кодстайла
- Процесс code review
- Инструкция по запуску тестов
Related to #23
```

### Пример с Local task
```
feat: Реализация моделей данных
- Модель Category с полями name, slug
- Модель Post с Markdown-конвертацией
- Автоматическая генерация slug
Local task #2
```

## 6. Интеграция с GitHub
```mermaid
graph TD
    A[Коммит с ключевым словом] --> B{Условия срабатывания}
    B -->|1. Ключевое слово Closes/Fixes| C[Автоматическое закрытие]
    B -->|2. Ссылка #issue в теле| D[Связь с задачей]
    B -->|3. Слияние в main/master| E[Триггер обработки]
```

### Автоматическое закрытие задач
- Работает "из коробки" для публичных репозиториев
- Для приватных: убедитесь, что workflow разрешает автоматическое закрытие
- Поддерживаемые ключевые слова:
  - `Closes #123`
  - `Fixes #45`
  - `Resolves issue #67`

### Настройка
1. Для GitHub:
   - Требуется слияние в ветку по умолчанию (main/master)
   - Добавьте файл `.github/workflows/auto-close.yml` для кастомных сценариев

## 7. Рекомендации
1. Язык: русский
2. Длина заголовка: ≤50 символов
3. Тело: 3-5 пунктов для средних изменений
4. Ссылки на задачи в конце тела коммита
5. Для задач из локальной системы используйте `Local task #X` в теле коммита

## 8. Связь с локальными задачами

Проект использует систему задач, описанных в `doc/tasks/tasks.md`. Для связи коммитов с этими задачами:

```mermaid
graph LR
    A[Локальная задача] --> B(Коммит)
    B --> C{Связь}
    C -->|Ссылка| D[Local task #X]
    C -->|Синхронизация| E[GitHub issue]
```

- **Local task #X**: Указывает на соответствие коммита задаче X из локальной системы
- Пример: `Local task #3` для задачи "Настройка S3-хранилища"

### Рекомендации по синхронизации
1. При создании GitHub issue укажите соответствующий номер локальной задачи в описании
2. Используйте одинаковые номера задач в локальной системе и GitHub
3. Обновляйте статус задачи в `tasks.md` при закрытии issue
